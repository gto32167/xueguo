# BUG 修复与验证

## 标准流程

```text
TAPD BUG -> 复现 -> 根因 -> 回归测试 -> 修复 -> L1/L2 -> VPN -> L3/L4/L5 -> 证据
```

## 按风险选择流程

BUG 先标记 `change_level`。L0 只需记录范围、原因和最小检查；L1 记录复现、根因、回归测试并验证受影响模块；L2/L3 才进入增量或完整 Spec 流程。修复中发现接口、数据、权限、状态、跨模块或不可逆影响时，必须升级级别。

## 验证分级（与 change_level 独立）

`change_level` 的 L0-L3 表示流程风险；本节的 L1-L5 表示验证环境和证据深度。两者不要互相填入。

| 等级 | 内容 | 环境 |
|---|---|---|
| L1 | 纯函数、规则、状态和参数校验 | 无服务 |
| L2 | DAO、Service、Controller 切片 | 可选联调测试库 |
| L3 | 单服务接口，其他服务使用 Mock | 最少服务 |
| L4 | 已部署环境 API 探针 | 人工 VPN |
| L5 | 浏览器端到端验收 | 人工 VPN |

每个 BUG 只选择能证明修复有效的最小验证组合。验证报告必须区分 `MOCK_VERIFIED`、`CONTRACT_VERIFIED`、`SANDBOX_VERIFIED` 和 `RELEASE_VERIFIED`，不能把 Mock 通过写成真实联调通过。

## 证据要求

- 修复前复现步骤。
- 根因和影响范围。
- 回归测试类与执行命令。
- API 响应摘要或页面截图索引。
- 未执行验证和原因。
- 仍需部署、VPN 或第三方资料确认的风险。
