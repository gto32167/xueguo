# 变更风险分级与最小充分流程

## 目标

流程成本必须和变更风险匹配。所有变更都要留下足够的责任、范围和验证记录，但小范围修复不需要完整执行 `spec -> analyze -> contract -> implement -> verify -> finish`。

## 四级路由

| 级别 | 适用场景 | 最小产出 | 最小验证 |
|---|---|---|---|
| L0 | 文案、日志、局部样式、纯格式调整、明确的局部机械修复 | 轻量变更记录或提交说明 | 直接检查、相关静态检查或单元测试 |
| L1 | 单模块内部 BUG，不改变对外接口、数据含义、权限和状态流转 | BUG 卡或轻量变更记录，包含根因和回归测试 | 受影响模块的针对性测试或编译 |
| L2 | 跨模块行为、数据库字段、接口字段、消费者、依赖或状态逻辑变化 | 增量 Spec + Impact + Plan + Verify | 受影响模块验证，必要时契约或环境验证 |
| L3 | 对外契约删除、数据删除或迁移、资金、权限边界、历史数据重新解释等不可逆或高风险变化 | 完整 Spec + Change Request + 人工决策 + Verify | 分层验证、发布与回退/补偿证据 |

## 分级问题

`change_level` 是流程风险级别；BUG 卡中的 `verification_levels` 是验证深度，两者是独立维度。一个 L0 修复可以只做最小检查，一个 L2 变更也可能只需要验证层级 L1/L2，不能把两种级别混用。

依次回答以下问题：

1. 是否改变对外接口、共享 DTO、错误码或文档契约？
2. 是否改变数据库结构、数据含义、状态流转或历史数据解释？
3. 是否影响其他模块、仓库、消费者、权限范围或资金结果？
4. 是否引入新的技术方案、依赖、部署步骤或环境要求？
5. 是否包含删除、迁移、不可逆操作或需要人工批准的决定？

全部为否时，按 L0 或 L1 处理；第 1-4 项任一为是时至少为 L2；第 5 项为是时为 L3。验证深度仍按 BUG 验证文档的 L1-L5 选择，并单独记录在 `verification_levels`。

## 最小充分流程

### L0

- 可以直接修改，不创建完整 Feature Spec。
- 在轻量变更记录中写明改动范围、原因和验证命令。
- 不要求 `proposal.md`、`design.md`、`impact.md` 或完整 `tasks.md`。

### L1

- 先记录复现、根因、影响范围和回归测试。
- 只读取与受影响模块相关的代码和项目记忆。
- 只执行能够证明修复有效的最小验证组合。
- 没有跨模块影响时，不要求完整 Impact 和契约文档。

### L2/L3

- 继续使用完整黄金路径和现有人工责任门禁。
- Acceptance Criteria 必须有唯一编号，并在任务和验证报告中通过 `spec_refs` 引用。
- L2/L3 在实现前必须通过 `feature-analyze`；实现后必须逐条回填 AC/SM 验证证据，并检查 Constitution。
- Plan 暴露出未声明的边界、接口、数据或依赖时，先回写 Spec，再继续实施。

## 升级条件

实施中出现以下任一情况，必须提升级别并补齐缺失产出：

- 实际影响范围超过原记录的模块或仓库。
- 需要修改接口、共享字段、数据库、权限、状态或发布配置。
- 原因或验收标准无法用现有记录清楚证明。
- 修复需要新增依赖、迁移、部署或人工决策。
- 最小验证失败且根因不再局限于原定范围。

分级是流程路由，不是降低质量门槛。L0/L1 仍必须留下可追溯的责任和验证证据。
